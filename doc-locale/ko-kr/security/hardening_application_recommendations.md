일반 강화 지침은 [주요 강화 문서](hardening.md)를 참조하세요.

웹 인터페이스를 통해 GitLab 인스턴스의 강화 권장 사항을 제어합니다.

## 전제 조건 {#prerequisites}

관리자 액세스 권한이 있어야 합니다.

## 시스템 hook {#system-hooks}

1. 오른쪽 위 모서리에서 **운영자**를 선택합니다.
1. 왼쪽 사이드바에서 **시스템 hook**을 선택합니다.

일반적인 강화된 환경에서 내부 정보는 시스템 외부로 전송되거나 저장되지 않습니다. 오프라인 환경 시스템의 경우 이것이 암시됩니다. 시스템 hook은 환경의 로컬 이벤트가 트리거에 기반하여 환경 외부로 정보를 전달하는 방법을 제공합니다.

이 기능의 사용 사례는 특히 원격 시스템을 통한 시스템 모니터링에서 지원됩니다. 그러나 시스템 hook을 배포할 때는 극도의 주의를 기울여야 합니다. 강화된 시스템의 경우 오프라인 환경으로 의도된 경우 서로 통신할 수 있는 신뢰할 수 있는 시스템의 경계를 적용해야 하므로 모든 hook(시스템, 웹 또는 파일)은 해당 신뢰할 수 있는 시스템하고만 통신해야 합니다. 시스템 hook을 통한 통신에는 TLS가 강력히 권장됩니다.

## 푸시 규칙 {#push-rules}

1. 오른쪽 위 모서리에서 **운영자**를 선택합니다.
1. 왼쪽 사이드바에서 **푸시 규칙**을 선택합니다.

다음 항목이 선택되어 있는지 확인합니다:

- **인증되지 않은 사용자 거부**
- **사용자가 `git push`로 Git 태그를 제거하지 못하도록 허용 안 함**
- **커밋 작성자가 GitLab 사용자인지 확인**
- **비밀 파일 푸시 방지**

이러한 조정은 확립되고 인증된 사용자로의 푸시를 제한하는 데 도움이 됩니다.

## 배포 키 {#deploy-keys}

1. 오른쪽 위 모서리에서 **운영자**를 선택합니다.
1. 왼쪽 사이드바에서 **키 배포**를 선택합니다.

공개 배포 키는 인스턴스의 **전체** 프로젝트에 읽기 또는 읽기/쓰기 액세스를 제공하는 데 사용되며 원격 자동화가 프로젝트에 액세스하기 위한 것입니다. 공개 배포 키는 강화된 환경에서 사용하면 안 됩니다. 배포 키를 사용해야 하는 경우 프로젝트 배포 키를 대신 사용하세요. 자세한 내용은 [배포 키](../user/project/deploy_keys/_index.md) 및 [프로젝트 배포 키](../user/project/deploy_keys/_index.md#create-a-project-deploy-key) 설명서를 참조하세요.

## 일반 {#general}

1. 오른쪽 위 모서리에서 **운영자**를 선택합니다.
1. 왼쪽 사이드바에서 **설정** > **일반**을 선택합니다.

강화 조정은 4개 섹션에서 수행할 수 있습니다.

### 표시 및 액세스 제어 {#visibility-and-access-control}

다음 설정의 기본값은 **비공개**입니다:

- **Default project visibility**
- **Default snippet visibility**
- **Default group visibility**

프로젝트, 스니펫 또는 그룹에 특정 액세스 권한이 부여된 사용자만 이러한 리소스에 액세스할 수 있습니다. 필요에 따라 또는 생성 시에 나중에 조정할 수 있습니다. 이는 의도하지 않은 또는 악의적인 정보 공개를 방지하는 데 도움이 됩니다.

보안 정책 및 태세에 따라 **Restricted visibility level**을 **공개**로 설정하기를 원할 수 있으며, 이는 인증되지 않은 사용자가 사용자 프로필을 볼 수 없도록 방지합니다.

**소스 가져오기**에서 필요한 소스만 선택합니다.

일반적인 배포에서는 **활성화된 Git 액세스 프로토콜**이 **SSH 및 HTTP(S) 모두**로 설정되어 있으나, Git 프로토콜 중 하나를 사용자가 사용하지 않는 경우 **SSH만** 또는 **HTTP(S)만**으로 각각 설정합니다. 이는 공격 표면을 줄이는 데 도움이 됩니다.

SSH 키 유형의 경우 다음이 권장됩니다: `ED25519` (및 `ED25519-SK`), `RSA`, `ECDSA` (및 `ECDSA-SK`) 순서입니다. `ED25519`은 `RSA`과 동일한 수준의 보안을 제공하며, `RSA`이 2048비트 이상으로 설정된 경우입니다. 하지만 `ED25519` 키는 더 작고 알고리즘이 훨씬 빠릅니다.

`ED25519-SK` 및 `ECDSA-SK`는 모두 `-SK`으로 끝나며, 이는 "보안 키"를 의미합니다. `-SK` 유형은 FIDO/U2F 표준과 호환되며 하드웨어 토큰(예: YubiKey) 사용과 관련됩니다.

`DSA`은 "금지됨"으로 설정해야 합니다. `DSA`는 알려진 결함이 있으며 많은 암호학자들은 `ECDSA` 사용을 의심하고 지원하지 않습니다.

GitLab이 FIPS 모드인 경우 다음을 사용합니다:

- FIPS 모드에서 실행 중인 경우:
  - `RSA`을 사용하고 **Must be at least 2048 bits**으로 설정합니다.
  - `ECDSA` (및 `ECDSA-SK`)을 사용하고 **Must be at least 256 bits**으로 설정합니다.
  - 다른 모든 키 유형을 **Are forbidden**으로 설정합니다. `RSA`과 `ECDSA`은 모두 FIPS 사용에 승인되었습니다.
- FIPS 모드에서 실행하지 않는 경우 `ED25519`을 사용해야 하며 `RSA`도 사용할 수 있습니다:
  - `ED25519` (및 `ED25519-SK`)을 **Must be at least 256 bits**으로 설정합니다.
  - `RSA`을 사용하는 경우 **Must be at least 2048 bits**으로 설정합니다.
  - 다른 모든 키 유형을 **Are forbidden**으로 설정합니다.
- 새 사용자 그룹에 대한 인스턴스를 설정하는 경우 보안 강화를 위해 최대 비트 설정으로 사용자 SSH 키 정책을 정의합니다.

강화된 환경에서 RSS 피드는 일반적으로 필요하지 않으며 **피드 토큰**에서 **Disabled feed token** 확인란을 선택합니다.

모든 사용자가 특정 IP 주소에서 오는 경우 **Global-allowed IP ranges**를 사용하여 해당 주소만 특별히 허용합니다.

**Visibility and access control**에 대한 자세한 내용은 [표시 및 액세스 제어](../administration/settings/visibility_and_access_controls.md)를 참조하세요. SSH 설정에 대한 내용은 [SSH 키 제한](ssh_keys_restrictions.md)을 참조하세요.

### 계정 및 제한 {#account-and-limit}

강화 목적을 위해 **Gravatar 활성화됨** 옆의 확인란이 선택되어 있지 않은지 확인합니다. 모든 불필요한 통신은 제한되어야 하며 일부 환경에서는 제한될 수 있습니다. 계정 아바타는 사용자가 수동으로 업로드할 수 있습니다.

이 섹션의 설정은 사용자에게 자신의 특정 표준을 사용자 지정 구현하도록 적용하는 데 도움이 됩니다. 다양한 시나리오가 너무 많고 다양하기 때문에 [계정 및 제한 설정 설명서](../administration/settings/account_and_limit_settings.md)를 검토하고 변경 사항을 적용하여 자신의 정책을 적용해야 합니다.

### 새 계정 제한 {#new-account-restrictions}

**새 사용자 계정 허용** 확인란이 선택되어 있지 않은지 확인하여 강화된 인스턴스에서 새 사용자 계정을 만들 수 없도록 합니다.

**이메일 확인 설정**에서 **Hard**가 선택되었는지 확인합니다. 사용자는 액세스 권한이 부여되기 전에 이메일 주소를 확인해야 합니다.

**최소 비밀번호 길이(문자 수)** 기본 설정은 12로, 추가 인증 기술을 사용하는 한 적절해야 합니다. 비밀번호는 복잡해야 하므로 다음 4개 확인란이 모두 선택되었는지 확인합니다:

- **숫자 필요**
- **대문자 필요**
- **소문자 필요**
- **기호 필요**

모든 사용자가 이메일 주소에 특정 도메인을 사용하는 동일한 조직에 속하는 경우 **사용자 생성이 허용된 도메인**에 해당 도메인을 나열합니다. 이는 다른 도메인의 이메일 주소를 가진 사람들이 가입하는 것을 방지합니다.

자세한 내용은 [새 사용자 계정 제한](../administration/settings/sign_up_restrictions.md)을 참조하세요.

### 로그인 제한 {#sign-in-restrictions}

2단계 인증 (2FA)을 모든 사용자에 대해 활성화해야 합니다. **이중 인증** (2FA) 옆의 확인란이 선택되었는지 확인합니다.

**이중 인증 유예 기간**의 기본 설정은 48시간입니다. 이를 8시간과 같은 훨씬 낮은 값으로 조정해야 합니다.

**운영자 모드 활성화** 옆의 확인란이 선택되었는지 확인하여 **운영자 모드**가 활성화되도록 합니다. 이를 위해서는 관리자 액세스 권한이 있는 사용자가 관리 작업을 수행하기 위해 추가 인증을 사용해야 하며, 사용자가 추가 2FA를 적용합니다.

**알 수 없는 로그인에 대한 이메일 알림**에서 **이메일 알림 활성화**가 선택되었는지 확인합니다. 인식되지 않는 위치에서 로그인이 발생할 때 사용자에게 이메일을 보냅니다.

자세한 내용은 [로그인 제한](../administration/settings/sign_in_restrictions.md)을 참조하세요.

## 통합 {#integrations}

1. 오른쪽 위 모서리에서 **운영자**를 선택합니다.
1. 왼쪽 사이드바에서 **설정** > **연동**을 선택합니다.

일반적으로 관리자가 사용을 제어하고 모니터링하는 한 통합은 강화된 환경에서 문제가 없습니다. 로컬 프로세스나 인증된 사용자가 수행할 경우 제한하거나 감사할 액세스 수준을 일반적으로 필요로 하는 외부 시스템의 작업을 트리거하는 작업 및 프로세스를 허용하는 통합에 주의합니다.

## 측정항목 및 프로파일링 {#metrics-and-profiling}

1. 오른쪽 위 모서리에서 **운영자**를 선택합니다.
1. 왼쪽 사이드바에서 **설정** > **측정항목 및 프로파일링**을 선택합니다.

강화의 주요 초점은 **사용 통계**입니다:

- **버전 점검 활성화**가 선택되었는지 확인해야 합니다. 이는 최신 버전의 GitLab을 실행 중인지 확인하며 새 기능 및 보안 패치가 포함된 새 버전이 자주 출시되므로 최신 상태를 유지하는 데 도움이 됩니다.

- 환경이 격리되어 있거나 조직 요구 사항이 데이터 수집 및 통계 보고를 소프트웨어 공급자로 제한하는 경우 **Enable service ping** 기능을 끄야 할 수 있습니다.

## 네트워크 {#network}

1. 오른쪽 위 모서리에서 **운영자**를 선택합니다.
1. 왼쪽 사이드바에서 **설정** > **네트워크**를 선택합니다.

속도 제한을 활성화하는 설정의 경우 선택되었는지 확인합니다. 기본값이 좋아야 합니다. 또한 액세스를 활성화하는 많은 설정이 있으며 이들 모두를 선택 해제해야 합니다.

이러한 조정을 수행한 후 성능 및 사용자 요구를 충족하도록 시스템을 미세 조정할 수 있으며, 이는 속도 제한을 비활성화하고 조정하거나 액세스를 활성화해야 할 수 있습니다. 다음은 유의할 몇 가지 주목사항입니다:

- **아웃바운드 요청**에서 제한된 수의 시스템에 대한 액세스를 열어야 하는 경우 IP 주소 또는 호스트 이름을 지정하여 해당 시스템으로의 액세스만 제한할 수 있습니다. 이 섹션에서도 모든 액세스를 허용하는 경우 **Enforce DNS rebinding attack protection**을 선택했는지 확인하세요.

- **Notes rate limit** 및 **Users API rate limit** 아래에서 필요한 경우 특정 사용자를 해당 제한에서 제외할 수 있습니다.
