## Description {#description}

L'application a été détectée comme renvoyant des données d'erreur telles que des traces de pile. Selon les données contenues dans le message d'erreur, ces informations pourraient être utilisées par un attaquant pour mener d'autres attaques. Bien que les traces de pile soient utiles lors du développement et du débogage, elles ne doivent pas être présentées aux utilisateurs lorsqu'une erreur se produit.

## Remédiation {#remediation}

Les applications doivent gérer les conditions d'exception en interne et associer les types de défaillances connus à des codes d'erreur pouvant être affichés à l'utilisateur. Ces codes d'erreur doivent être personnalisés pour l'application et renvoyés avec le code d'erreur HTTP approprié.

Lorsqu'une erreur se produit, l'application identifie le type ou la classe de l'erreur et affiche une valeur numérique à l'utilisateur. Les requêtes doivent également être suivies afin que, lorsqu'un utilisateur se voit présenter un code d'erreur, celui-ci soit associé à un identifiant de requête correspondant. Les équipes d'assistance peuvent alors corréler l'erreur HTTP, le code d'erreur personnalisé et l'identifiant de requête dans les fichiers journaux afin de déterminer la cause racine de l'erreur sans divulguer de détails à l'utilisateur final.

Exemple de renvoi d'erreurs personnalisées :

```plaintext
HTTP/1.1 500 Internal Server Error
...
Error [0004] Occurred, please contact support or re-try your request again shortly.
Request ID [a4bc91def12]
...
```
