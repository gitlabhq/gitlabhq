このページでは、PostgreSQLの自動バキュームをチューニングする方法、および一般的な自動バキュームの問題をトラブルシューティングする方法について説明します。

## 自動バキュームの仕組み {#how-autovacuum-works}

PostgreSQLは[マルチバージョン同時実行制御（MVCC）](https://www.postgresql.org/docs/current/mvcc-intro.html)を使用します。行を更新または削除しても、PostgreSQLはすぐに古い行バージョンを削除しません。代わりに、PostgreSQLは古いバージョンをデッドとしてマークし、実行中のトランザクションがそれを参照できなくなるまで保持します。自動バキュームとは、これらのデッド行バージョン（デッドタプルとも呼ばれる）を削除するバックグラウンドプロセスです。これらが占有する領域を再利用し、プランナーの統計情報を更新し、可視性マップを維持します。

自動バキュームは、データベースの健全性にとって重要です。自動バキュームがないと、デッド行がテーブルおよびインデックスの肥大化として蓄積されます。肥大化はクエリを遅くし、ディスク領域を無駄にし、バックアップとメンテナンスの時間を増加させます。自動バキュームは、データベースへの書き込みを停止させる[トランザクションIDのラップアラウンド](https://www.postgresql.org/docs/current/routine-vacuuming.html#VACUUM-FOR-WRAPAROUND)も防止します。

### 自動バキュームが実行されるタイミング {#when-autovacuum-runs}

自動バキュームは定期的に各テーブルをチェックし、デッドタプルの数が次のしきい値を超えると、バキュームを実行します:

```plaintext
autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × number_of_live_tuples
```

デフォルトでは、PostgreSQLは`autovacuum_vacuum_scale_factor`を`0.2`に設定します。その後、PostgreSQLは行の20％がデッドになった場合にのみテーブルをバキュームします。大規模なテーブルでは、20％は多数のデッドタプルになります。そのため、自動バキュームが処理を行う前に、テーブルが長時間肥大化します。この遅延を軽減するため、GitLab Linuxパッケージインストールでは、デフォルトで`autovacuum_vacuum_scale_factor`を`0.02`（2％）に引き下げています。最大のテーブルや頻繁に更新されるテーブルでは、それでもテーブルごとに低い値が必要になる場合があります。[大規模なテーブルを個別にチューニングする](#tune-large-tables-individually)を参照してください。

## 推奨される自動バキューム設定 {#recommended-autovacuum-settings}

GitLab Linuxパッケージインストールには、ほとんどのワークロードに適した自動バキュームのデフォルト設定が用意されています。[モニタリング](#monitor-autovacuum)により、自動バキュームがデッドタプルに追いつけないことが判明した場合は、これらの設定を変更してください。目標は、データベースのI/Oを枯渇させることなく、ワークロードが作成するのと同じ速さで自動バキュームにデッドタプルを再利用させることです。

最も影響の大きい変更は、通常、`autovacuum_vacuum_cost_limit`の引き上げ、`autovacuum_max_workers`の引き上げ、および最大のテーブルのスケールファクターの引き下げです。このセクションの値は出発点として扱い、自身のワークロードに対して検証してください。

### クラスター全体の設定 {#cluster-wide-settings}

GitLab Linuxパッケージインストールの場合は、`/etc/gitlab/gitlab.rb`でクラスター全体の値を設定してから、`sudo gitlab-ctl reconfigure`を実行します。

```ruby
postgresql['autovacuum_max_workers'] = "<value>"
postgresql['autovacuum_vacuum_cost_limit'] = "<value>"
postgresql['autovacuum_vacuum_cost_delay'] = "<value>"
postgresql['maintenance_work_mem'] = "<value>"
```

[外部PostgreSQLインスタンス](external.md)の場合は、代わりに`postgresql.conf`で同じパラメータを設定してから、PostgreSQLをリロードします:

```ini
autovacuum_max_workers = <value>
autovacuum_vacuum_cost_limit = <value>
autovacuum_vacuum_cost_delay = <value>
maintenance_work_mem = <value>
autovacuum_work_mem = <value>
```

`SELECT pg_reload_conf();`を使用するか、サービスをリロードすることで、PostgreSQLをリロードします。両方のインストールタイプにおいて、`autovacuum_max_workers`などの設定にはPostgreSQLの完全な再起動が必要です。リロードや再設定だけでは不十分です。

次の設定は、自動バキュームが処理に追いつけるかどうかに最も大きな影響を与えます:

| 設定                          | 推奨値           | 説明                                                                                                                                                                                                                                                                                                                                                 |
|----------------------------------|-----------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `autovacuum_max_workers`         | vCPU数の約25％ | 同時に実行される自動バキュームプロセスの最大数。大規模なマルチコアのデータベースホストでは、デフォルト値が低すぎることがよくあります。各ワーカーはメモリとI/O負荷を増加させます。                                                                                                                                                                                  |
| `autovacuum_vacuum_scale_factor` | `0.01`から`0.02`            | 自動バキュームが実行される前にデッドになっている必要があるテーブルの行の割合。GitLabはPostgreSQLのデフォルト値を`0.02`に引き下げています。大規模で頻繁に更新されるテーブルでは、さらに低く設定してください。[大規模なテーブルを個別にチューニングする](#tune-large-tables-individually)を参照してください。                                                                                                          |
| `autovacuum_vacuum_cost_limit`   | SSDの場合は800                 | 自動バキュームが一時停止する前に蓄積するI/Oコスト。`-1`に設定すると、`vacuum_cost_limit`の値を継承します。その値は、最新のSSDベースのストレージのスループットを大幅に下回っています。明示的に設定してください。これを引き上げることが、最も影響の大きい変更であることが多いです。                                                                                                         |
| `autovacuum_vacuum_cost_delay`   | 2ミリ秒                        | 自動バキュームがコスト制限に達した後に一時停止する時間。自動バキュームをより積極的にするには、この値を下げてください。これを`0`に設定しないでください。[避けるべき設定](#settings-to-avoid)を参照してください。                                                                                                                                                                                      |
| `maintenance_work_mem`           | 1GBから2GB                | インデックスの作成などのメンテナンス操作用のメモリ。`autovacuum_work_mem`が`-1`の場合、各自動バキュームワーカーもデッドタプルを追跡するためにこれと同じ量のメモリを使用します。値が低いと、ワーカーが大規模なテーブルでインデックスを繰り返しスキャンするようになります。利用可能なRAMとワーカー数に応じてサイズを設定してください。                                                                   |
| `autovacuum_work_mem`            | 512MB                      | 各自動バキュームワーカーがデッドタプルを追跡するために使用するメモリ。`-1`に設定すると、ワーカーは`maintenance_work_mem`を継承します。その結果、自動バキュームの合計メモリはワーカー数に応じてスケールします。PostgreSQL 17では、このメモリの1GBの上限が撤廃されました。ワーカー数を引き上げる場合は、明示的に上限を設定してください。Linuxパッケージインストールでは、このパラメータを`gitlab.rb`で設定できません。 |
| `autovacuum_naptime`             | 数秒（オプション）    | 自動バキュームがデータベースのチェック間で待機する時間。変動が激しいデータベースでは、自動バキュームがより迅速に応答するよう、この値を下げてください。                                                                                                                                                                                                                                  |

### 大規模なテーブルを個別にチューニングする {#tune-large-tables-individually}

クラスター全体のスケールファクターが低くても、最大のテーブルは肥大化する可能性があります。これらのテーブルでは、PostgreSQLで直接、テーブルごとに低いスケールファクターまたはしきい値を設定してください。非常に大規模で頻繁に更新されるテーブルでは、`0.01`（1％）前後のスケールファクターが一般的です:

```sql
ALTER TABLE <table_name> SET (autovacuum_vacuum_scale_factor = 0.01);
```

テーブルごとの設定は、そのテーブルについてのみクラスター全体の値を上書きします。[モニタリング](#monitor-autovacuum)を使用して遅れているテーブルを見つけ、まず本番環境以外で変更をテストしてください。

### 避けるべき設定 {#settings-to-avoid}

> [!warning]
> 自動バキュームを無効化（`autovacuum = off`）しないでください。自動バキュームがないと、デッドタプルが蓄積します。その結果、データベースはトランザクションIDのラップアラウンドに向かいます。ラップアラウンドは、データベースへの書き込みを停止させます。

次の設定は避けてください:

- `autovacuum_vacuum_cost_delay = 0`は、I/Oスロットリングを削除します。その結果、自動バキュームは一時停止せずに実行され、ディスクI/Oを飽和させる可能性があります。クエリが遅くなります。
- 最大のテーブルにデフォルトのスケールファクターを使用すること。その結果、これらのテーブルのバキュームがあまりにもまれにしか行われなくなります。代わりにテーブルごとに低い値を設定してください。
- `autovacuum_vacuum_cost_limit`について`-1`の継承に依存すること。その結果、有効な値が別の設定内にあり、見落とす可能性があります。明示的に設定してください。

## 自動バキュームをモニタリングする {#monitor-autovacuum}

### データベース診断ページ {#database-diagnostics-page}

{{< history >}}

- Vacuumのアクティビティは、GitLab 19.2で[導入](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/239928)されました。
- 自動バキュームの設定と検出結果は、GitLab 19.4で[導入](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/242428)されました。
- テーブルごとの上書き設定とスケールファクターのリスクは、GitLab 19.5で[導入](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/245561)されました。

{{< /history >}}

データベース診断ページには、各データベースのVacuumのアクティビティと自動バキュームの設定が表示されます。

前提条件: 

- 管理者アクセス権が必要です。

ページを表示するには:

1. 右上隅で、**管理者**を選択します。
1. 左側のサイドバーで、**モニタリング** > **データベース診断**を選択します。

ページの2つのセクションが自動バキュームに関連しています。各セクションには、インストール内のデータベースごとに1つのカードがあります。

**Vacuumの情報**セクションには、**Vacuumのアクティビティ**パネルが含まれています。このパネルには、現在実行中のバキュームごとに1行が表示されます。列は、Table、Type、Running for、Phase、Heap scanned、Indexes processed、Dead tuples、Index passes、Delay timeです。行には次のバッジが付くことがあります:

- **アンチラップアラウンド**: バキュームがトランザクションIDのラップアラウンドを防止しています。このバキュームは自動的にキャンセルされません。終了させないでください。終了させた場合、データベースはデータを保護するためにシャットダウンする可能性があります。
- **長時間実行中**: バキュームが6時間以上実行されています。大規模なテーブルではこれくらいの時間がかかることがありますが、決して完了しないバキュームはブロックされているか、リソースが不足している可能性があります。
- **メモリ負荷**: バキュームに複数回のインデックスパスが必要でした。ヒープスキャンが完了する前に、デッドタプルストアがいっぱいになりました。`maintenance_work_mem`または`autovacuum_work_mem`を引き上げてください。

**自動バキュームの設定**セクションには、次のパネルが含まれています:

- **有効な設定**: データベースが実際に使用している自動バキュームの設定で、`pg_settings`から読み取られます。**ステータス**列には、チェックで検出された設定ミスがそれぞれマークされます。`autovacuum_vacuum_cost_limit`が`-1`の場合、パネルには`vacuum_cost_limit`から継承される有効な制限値も表示されます。
- **テーブルごとの上書き設定**: ストレージパラメータで自動バキュームのパラメータを設定しているテーブル。このパネルには、各テーブルのサイズ、推定行数、および上書き設定が表示されます。自動バキュームを無効にしているテーブルには、**自動バキューム無効**バッジが付きます。このパネルには、自動バキュームを無効にしているテーブルを先頭にして、最大50個のテーブルが表示されます。上書き設定を持つテーブルがない場合、このパネルは非表示になります。
- **スケールファクターのリスク**: 有効なスケールファクターが依然として高い大規模なテーブル。チェックで該当するテーブルが見つからない場合、このパネルは非表示になります。

一部の検出結果は、単一の設定ではなくテーブルに関するものです。これらの検出結果は、パネルの上にアラートとして表示されます。各検出結果の背景にある条件については、[自動バキュームの検出結果](#autovacuum-findings)を参照してください。

> [!note]
> **Vacuumのアクティビティ**パネルには、PostgreSQL 17以降が必要です。それより前のバージョンでは、パネルは空になります。Delay time列には、PostgreSQL 18以降が必要です。TypeおよびRunning for列、そして**アンチラップアラウンド**バッジには、他のバックエンドのアクティビティを読み取れるデータベースロールが必要です。`pg_monitor`のメンバーシップをロールに付与してください。このメンバーシップがない場合、進捗列は引き続き機能しますが、Type、Running for、Anti-wraparoundの各フィールドには`Not available`と表示されます。

自動バキュームはプライマリデータベースでのみ実行されるため、両方のセクションはプライマリデータベースから読み取ります。

### コンソールで診断をレポートする {#report-diagnostics-on-the-console}

{{< history >}}

- GitLab 19.4で[導入](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/251254)されました。
- 単一のチェック用のタスクは、GitLab 19.4で[導入](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/251735)されました。
- 単一のチェックに対するメニューの削除は、GitLab 19.5で[変更](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/257133)されました。

{{< /history >}}

UIにアクセスできない場合、またはスクリプトからレポートを取得したい場合は、Rakeタスクを使用してください。

Linuxパッケージインストールの場合:

```shell
sudo gitlab-rake gitlab:db:diagnostics
```

デフォルトでは、このタスクはすべてのデータベースについてレポートします。データベースを選択するには、その名前を渡します:

```shell
sudo gitlab-rake "gitlab:db:diagnostics[main,ci]"
```

自動バキュームのチェックのみを実行するには、専用のタスクを使用してください。これは同じデータベース名を受け付けます:

```shell
sudo gitlab-rake "gitlab:db:diagnostics:autovacuum_settings[main,ci]"
```

レポートは、最初にサマリーを表示し、その後各チェックのセクションを表示します。**自動バキューム設定**セクションには、各データベースの検出結果、有効な設定、テーブルごとの上書き設定、およびスケールファクターのリスクが一覧表示されます。

タスクはエラーを検出するとステータス`1`で終了するため、モニタリングジョブはその終了コードを使用できます。

ターミナルでは、このタスクは複数のチェックを実行する場合に、各セクションを開くメニューを表示します。1つのチェックのみを実行する場合、または出力をパイプまたはリダイレクトする場合、このタスクはレポート全体を表示します。

> [!note]
> Rakeタスクは設定のみをレポートします。Vacuumのアクティビティは表示しません。Vacuumのアクティビティは、[データベース診断ページ](#database-diagnostics-page)でのみ確認できます。

| テーブル無効     | テーブルごとの`autovacuum_enabled`   | エラー    | 1つ以上のテーブルで、ストレージパラメータに`autovacuum_enabled = false`が設定されています。これらのテーブルのデッドタプルは自動的に再利用されることはありません。**テーブルごとの上書き設定**パネルには、該当する各テーブルがマークされます。                                                                                                                                                            | `ALTER TABLE <table_name> RESET (autovacuum_enabled);`を使用して、各テーブルで自動バキュームを再度オンにしてください。                                                                                                                     |
| スケールファクターのリスク   | `autovacuum_vacuum_scale_factor` | 警告  | クラスター全体のスケールファクターが`0.1`以上で、かつ上位20個の最大テーブルのいずれかが10GiB以上であり、有効なスケールファクターが`0.1`以上です。Linuxパッケージインストールでは`0.02`が設定されています。そのため、この検出結果は、PostgreSQLのデフォルト値である`0.2`を維持している外部PostgreSQLインスタンスで主に表示されます。                                             | クラスター全体のスケールファクターを引き下げるか、一覧表示されたテーブルにテーブルごとの値を設定してください。[大規模なテーブルを個別にチューニングする](#tune-large-tables-individually)を参照してください。                                                              |

有効なスケールファクターは、設定されている場合はテーブルごとの上書き値であり、設定されていない場合はクラスター全体の値です。テーブルごとの`autovacuum_vacuum_threshold`は、テーブルを対象外にはしません。このチェックは、自動バキュームが無効になっているテーブルをスキップします。

> [!note]
> これらのチェックは、明らかな設定ミスのみをレポートします。これらのチェックはまた、[推奨される自動バキューム設定](#recommended-autovacuum-settings)の値よりも低いしきい値を使用します。設定がチェックに合格していても、ワークロードに対しては依然として低すぎる場合があります。たとえば、自動バキュームワーカー3つはチェックに合格しますが、vCPUが多いホストには低すぎます。

### デッドタプルとフリーズ年齢を確認する {#check-dead-tuples-and-freeze-age}

データベース診断ページもRakeタスクも、テーブルごとのデッドタプルやフリーズ年齢はレポートしません。代わりに、その情報についてはデータベースにクエリしてください。Linuxパッケージインストールでは、次のコマンドで接続します:

```shell
sudo gitlab-psql
```

デッドタプルが最も多いテーブルと、自動バキュームが最後にそれらを処理した時刻を確認するには:

```sql
SELECT schemaname, relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
WHERE n_dead_tup > 0
ORDER BY n_dead_tup DESC
LIMIT 20;
```

`n_dead_tup`のカウントが増加しており、`last_autovacuum`が古いか空である場合、自動バキュームがそのテーブルに追いついていないことを意味します。[自動バキュームがテーブルに追いつけない](#autovacuum-cannot-keep-up-with-a-table)を参照してください。

各テーブルのフリーズ年齢を確認するには:

```sql
SELECT n.nspname AS schema_name, c.relname AS table_name, age(c.relfrozenxid) AS xid_age
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'm')
  AND n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY xid_age DESC
LIMIT 20;
```

`xid_age`は、PostgreSQLが最後にテーブルをフリーズした後に実行されたトランザクションの数をカウントします。これを`autovacuum_freeze_max_age`と比較します。**有効な設定**パネルはこの値をレポートします。テーブルがこの値を超えると、PostgreSQLはそのテーブルに対してアンチラップアラウンドの自動バキュームを開始します。フリーズ年齢が上昇し続けることは、自動バキュームが十分な速さで行をフリーズできていないことを意味します。[トランザクションIDのラップアラウンドが迫っている](#transaction-id-wraparound-is-approaching)を参照してください。

## 一般的な問題のトラブルシューティングを行う {#troubleshoot-common-issues}

### 自動バキュームがテーブルに追いつけない {#autovacuum-cannot-keep-up-with-a-table}

テーブルは、自動バキュームが削除するよりも速くデッドタプルを蓄積します。デッドタプル数は増加し続け、テーブルは肥大化し、そのテーブルに対するクエリは遅くなります。この問題には、2つの一般的な原因があります:

- 高い変更率。データベースの移行、または行を頻繁に更新するエンドポイントは、自動バキュームがクリアするよりも速くデッドタプルを作成します。
- クラスター全体の設定を使用している、使用頻度の高いテーブル。大規模で頻繁に更新されるテーブルは、独自の自動バキューム設定が必要になることがよくあります。

遅れているテーブルを見つけるには、各テーブルのデッドタプル数と自動バキュームが最後に実行された時刻を確認してください。[自動バキュームをモニタリングする](#monitor-autovacuum)を参照してください。この問題を解決するには:

- テーブルごとに低いスケールファクターまたはしきい値を設定します。詳細については、[大規模なテーブルを個別にチューニングする](#tune-large-tables-individually)を参照してください。
- `autovacuum_vacuum_cost_limit`と`autovacuum_max_workers`を引き上げます。詳細については、[推奨される自動バキューム設定](#recommended-autovacuum-settings)を参照してください。
- 変動の原因が移行またはアプリケーションの変更である場合は、それを一時停止または元に戻します。

### トランザクションIDのラップアラウンドが迫っている {#transaction-id-wraparound-is-approaching}

PostgreSQLは、各トランザクションにID（XID）を割り当てます。最も古い未フリーズのXIDが古くなるにつれて、PostgreSQLは古い行をフリーズするためにアンチラップアラウンドの自動バキュームを実行します。これらのバキュームが完了できない場合、データベースは最終的にデータを保護するために書き込みの受け付けを停止します。

このリスクを追跡するには、各データベースおよびテーブルのフリーズ年齢をモニタリングしてください。[自動バキュームをモニタリングする](#monitor-autovacuum)を参照してください。フリーズ年齢が上昇し続けることは、自動バキュームが十分な速さで行をフリーズできていないことを意味します。

これを解決するには、自動バキュームが実行され、ブロックされていないことを確認してください。[自動バキュームがテーブルに追いつけない](#autovacuum-cannot-keep-up-with-a-table)を参照してください。データベースがすでに書き込みの受け付けを停止している場合は、[データベースがラップアラウンドによるデータ損失を回避するためにコマンドを受け付けない](../troubleshooting/postgresql.md#database-is-not-accepting-commands-to-avoid-wraparound-data-loss)に記載されている回復手順に従ってください。

### 自動バキュームが多くのリソースを使用する {#autovacuum-uses-too-many-resources}

自動バキュームは、他のクエリを遅くする可能性があるI/Oトラフィックを生成します。PostgreSQLは、コストベースの遅延によってこのトラフィックをスロットリングします。この遅延は、実行中のすべての自動バキュームワーカーに分散されます。そのため、実行されているワーカー数にかかわらず、合計I/Oへの影響はほぼ同じままになります。

他のクエリへの影響を減らすには、ワーカーがより頻繁に一時停止するように`autovacuum_vacuum_cost_delay`を引き上げてください。遅延を大きくすると、バキュームの速度が遅くなります。デッドタプルに追いつく必要性とのバランスを取ってください。遅延を`0`に設定しないでください。これにより、スロットリングが完全に解除されます。詳細については、[避けるべき設定](#settings-to-avoid)を参照してください。
