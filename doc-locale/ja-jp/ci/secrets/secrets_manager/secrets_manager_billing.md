GitLab Secrets Managerの使用は、2つのメーターに基づいて[GitLabクレジット](../../../subscriptions/gitlab_credits.md)を消費します:

- 保存されたシークレット: シークレットマネージャーに保持されているシークレットの数。1つのシークレットにつき月単位で測定されます。
- シークレット操作: シークレットのフェッチ（パイプライン、Kubernetesクラスター、またはAPI経由）は1回の操作とみなされます。シークレットの更新と削除は操作としてカウントされません。

## GitLabクレジットの消費 {#gitlab-credits-consumption}

GitLab Secrets Managerで消費されるGitLabクレジットは、トップレベルグループ（ネームスペース）のサブスクリプションで利用可能な[月次コミットメントプール](../../../subscriptions/gitlab_credits.md#monthly-commitment-pool)と[オンデマンドクレジット](../../../subscriptions/gitlab_credits.md#on-demand-credits)から差し引かれます。グループのプロジェクトおよびサブグループ全体でのシークレットマネージャーの使用は、トップレベルグループのクレジットを消費します。

> [!note]
> 各ユーザーに割り当てられる[含まれるクレジット](../../../subscriptions/gitlab_credits.md#included-credits)は、GitLab Secrets Managerには適用されません。

GitLabクレジットの使用上限は、シークレットマネージャーの使用を制限しません。使用量が個々のユーザーに帰属しないため、ユーザーごとの上限は適用されず、ネームスペースの使用上限はシークレットマネージャーの消費をブロックしません。

シークレットの保存と操作に対して、以下のレートに基づいてクレジットが消費されます:

| タイプ           | レート                 | クレジット | 詳細 |
|----------------|-----------------------|---------|---------|
| 保存されたシークレット | シークレット1つにつき、月額 | 1       | クレジット消費は、シークレットが存在する期間に基づいて日割りで計算されます。例えば、2つのシークレットを半月間保存すると、1クレジットを消費します。 |
| シークレットの読み取り   | 2,500回の読み取り       | 1       | すべてのシークレットに対するシークレット読み取り操作。CI/CDジョブ、シークレットマネージャーAPI、またはインテグレーション（ESO、Terraform、OpenBao CLI）によるシークレットの取得が含まれます。 |

[GitLabクレジットダッシュボード](../../../subscriptions/gitlab_credits_dashboard.md)でクレジット使用量を確認管理できます。

### CI/CDジョブでの使用 {#in-cicd-jobs}

CI/CDジョブで正常にフェッチされた各シークレットは、たとえ後でジョブが失敗した場合でも、1回の読み取り操作としてカウントされます。複数のシークレットを参照するジョブは、各シークレットに対して1回の読み取り操作を実行します。ジョブを再試行すると、シークレットは再度フェッチされます。

読み取り操作が失敗した場合、シークレット操作はクレジットを消費しません。失敗するケースは以下のとおりです:

- 参照されたシークレットが存在しない場合。
- 権限エラーにより読み取りが失敗した場合。

### 例 {#examples}

さまざまな状況におけるシークレットの月間予想消費量を把握するために、いくつかの例を挙げます:

- 25個のシークレットを保存し、月に500回のパイプライン実行があり、パイプラインごとに5個のシークレットを読み取る小規模チーム。
  - ストレージ: 25シークレット = 25クレジット
  - 操作: 2,500回の読み取り = 1クレジット
  - 月額合計: 26クレジット
- 開発、ステージング、本番環境で120個のシークレットを使用し、月に2,000回のパイプライン実行があり、パイプラインごとに5個のシークレットを読み取るマルチ環境アプリケーション。
  - ストレージ: 120シークレット = 120クレジット
  - 操作: 10,000回の読み取り = 4クレジット
  - 月額合計: 124クレジット
- 1,000個のシークレットを保存し、月に50,000回のパイプライン実行があり、パイプラインごとに10個のシークレットを読み取るエンタープライズレベルの使用。
  - ストレージ: 1,000シークレット = 1,000クレジット
  - 操作: 500,000回の読み取り = 200クレジット
  - 月額合計: 1,200クレジット

## サブスクリプションが終了した場合 {#when-your-subscription-ends}

ネームスペースのPremiumまたはUltimateサブスクリプションがキャンセルまたは期限切れになった場合、シークレットマネージャーはサブスクリプション終了日から14日間の猶予期間に入ります。

猶予期間中:

- パイプラインとサービスアカウントは、引き続きシークレットの読み取り操作を実行できます。
- シークレットを作成、更新、または削除することはできません。

猶予期間が終了すると、シークレット操作はブロックされます。GitLabはシークレットを削除せず、UIで引き続き表示できます。

完全なアクセスを復元するには、サブスクリプションを更新してください。

## ベータ終了 {#end-of-beta}

GitLab Secrets Managerのベータ使用ではGitLabクレジットは消費されません。GitLab.comのベータは2026年9月21日に終了します。

ベータ終了前のいつでも、トライアルを開始して一時的な評価クレジットを使用できます。トライアル終了時にサービスの中断を避けるため、サブスクリプションにGitLabクレジットが利用可能であることを確認する必要があります。

トライアルを開始しない場合、GitLab Secrets Managerはベータ終了時に無効になります。

## トライアルを開始 {#start-a-trial}

30日間の無料トライアルでGitLab Secrets Managerを評価できます。トライアルでは、保存されたシークレットおよびシークレット操作のために、500の[一時評価クレジット](../../../subscriptions/gitlab_credits.md#temporary-evaluation-credits)プールが提供されます。

トライアルは、以下のいずれかが先に発生した場合に終了します:

- アクティベーションから30日経過した場合。
- すべての一時評価クレジットが消費された場合。

一時評価クレジットはネームスペース全体で共有され、ユーザーごとに割り当てられるものではありません。これらはロールオーバーせず、期限切れ後は使用できません。

サブスクリプションに対してトライアルをアクティベートできるのは1回のみです。ネームスペースが以前にトライアルを使用したことがある場合、別のトライアルをアクティベートする資格はありません。

前提条件: 

- トップレベルグループのオーナーロールが必要です。

1. トップバーで**検索または移動先**を選択し、トップレベルグループを見つけます。
1. 左側のサイドバーで**安全** > **Secrets Manager**を選択します。
1. **30日間のトライアルを開始**を選択します。

トライアル終了時:

- サブスクリプションに[利用可能なGitLabクレジット](../../../subscriptions/gitlab_credits.md)がある場合、使用は中断なく継続され、月次コミットメントプールから、次いでオンデマンドクレジットから差し引かれます。
- GitLabクレジットにアクセスできない場合、シークレットマネージャーの操作はブロックされ、読み取り操作および依存するパイプラインは失敗します。アクセスを復元するには、[GitLabクレジットを購入する](../../../subscriptions/gitlab_credits.md#buy-gitlab-credits)必要があります。

## GitLab Self-Managedでアドオンを有効にする {#enable-the-add-on-on-gitlab-self-managed}

{{< details >}}

- プラン: Premium、Ultimate
- 提供形態: GitLab Self-Managed
- ステータス: 実験的機能

{{< /details >}}

{{< history >}}

- GitLab 19.4で`secrets_manager_paid_experience`[機能フラグ](../../../administration/feature_flags/_index.md)とともに[導入](https://gitlab.com/gitlab-org/gitlab/-/work_items/628115)されました。デフォルトでは無効になっています。

{{< /history >}}

> [!flag]
> この機能の利用可否は、機能フラグによって制御されます。詳細については、履歴を参照してください。この機能はテストには利用できますが、本番環境での使用には適していません。

管理者は、トライアルを開始せずに、GitLab Self-Managedインスタンスで有料のシークレットマネージャーアドオンを有効にできます。

前提条件: 

- インスタンスへの管理者アクセス権。
- サブスクリプションがGitLabサブスクリプションサービスと同期されるように、オンラインのクラウドライセンスが必要です。
- Customers Portalでサブスクリプションの使用量課金条件（オンデマンド課金）が承認されていること。

ライセンスがないインスタンス、またはトライアルライセンスのみのインスタンスは、アドオンを有効にする資格がありません。

### オフライン環境 {#offline-environments}

オフライン環境では、シークレットマネージャーアドオンは、サブスクリプションのアクティベーションコードによってアクティベートされます。ミューテーションを実行する必要はなく、オフラインライセンスではエラーが返されます。

### APIでアドオンを有効にする {#enable-the-add-on-with-the-api}

[GraphQL API](../../../api/graphql/_index.md)でアドオンを有効にするには:

1. 管理者アカウントでインスタンス内のGraphiQLを開きます（例: `https://gitlab.example.com/-/graphql-explorer`）。
1. GraphiQLで、次のミューテーションを入力します。

   ```graphql
   mutation {
     secretsManagerInstanceEnableAddOn(input: {}) {
       entitlement { state }
       errors
     }
   }
   ```

成功した場合、ミューテーションは`entitlement.state`に対して`PAID`を返します。失敗した場合、`entitlement`は`null`であり、`errors`には理由が含まれます。部分的な失敗の後、再度ミューテーションを送信できます。これは冪等であり、変換を二重に記録することはありません。

アドオンを有効にすると、GitLabは、インスタンスがまだ登録されていない場合はシークレットマネージャーに登録し、サブスクリプションの有料意図を記録します。その後、インスタンスのグループとプロジェクト全体でのシークレットマネージャーの使用は、このページで前述したレートでGitLabクレジットを消費します。グループとプロジェクトは、誰かがシークレットを初めて作成する際に、独自のシークレットマネージャーをプロビジョニングします。

管理者エリアからアドオンを有効にするボタンが[イシュー623334](https://gitlab.com/gitlab-org/gitlab/-/work_items/623334)で提案されています。

後でシークレットマネージャーからインスタンスの登録を解除した場合、有料アドオンの意図もクリアされます。
