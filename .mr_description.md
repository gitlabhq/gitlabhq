## What does this MR do and why?

Adds granular (fine-grained) personal access token authorization to the 40 user & collaboration GraphQL mutations from `config/authz/graphql/authorization_todo.txt` (group 11 of the mutation authorization effort), following the [GraphQL implementation guide](https://docs.gitlab.com/development/permissions/granular_access/graphql_implementation_guide/).

For each mutation this MR:

- adds an `authorize_granular_token` directive with the appropriate permission and boundary,
- creates or reuses raw permission definitions and assignable permissions,
- adds the shared-example authorization test per declared boundary type,
- removes the mutation's line from `config/authz/graphql/authorization_todo.txt`,
- regenerates `doc/auth/tokens/fine_grained_access_tokens_graphql.md`.

### Permissions

**Reused raw permissions (3):** `update_custom_attribute`, `delete_custom_attribute` (existing assignable permissions already cover the `instance` boundary these admin-only user mutations need), and `delete_timelog` (raw permission existed; it was not yet part of any assignable permission).

**New raw permissions (22):** `create/update/delete/award/revoke_achievement`, `update/delete_user_achievement`, `create/delete_award_emoji`, `create/update/delete_saved_reply`, `create/update_crm_contact`, `create/update_crm_organization`, `update_placeholder_reassignment`, `create_timelog`, `create/delete_custom_emoji`, `create_callout`, `update_commit_email`.

Five of these names (`award_achievement`, `create_custom_emoji`, `create_timelog`, `delete_custom_emoji`, `update_user_achievement`) are existing policy abilities that now get definition files, so their entries are removed from `config/authz/permissions/definitions_todo.txt`.

**Assignable permissions:** `create_award_emoji`/`delete_award_emoji` are added to the existing `create_work_item`/`delete_work_item` assignable permissions, mirroring how the per-noteable award emoji raw permissions and `create_note`/`delete_note` are bundled there. The remaining capabilities have no fitting existing assignable permission, so new ones are created: achievement (create/update/delete/award — award bundles the revoke raw permission), saved reply (create/update/delete), CRM contact and organization (create/update each), timelog (create/delete), custom emoji (create/delete), callout (create), commit email (update), and placeholder reassignment (update, next to the existing create/read).

### Judgment calls

- **`UserAchievementsDelete` uses the group boundary:** despite the mutation name, `destroy_user_achievement` is a group-owner ability (deleting an awarded achievement), not a recipient ability, so the boundary is the awarding group.
- **One permission across sibling scopes:** saved replies use a single `create/update/delete_saved_reply` permission with `user`, `group`, and `project` boundaries instead of per-scope permissions, per the no-boundary-in-name convention. Same idea for `create_callout` (user + group).
- **`update_placeholder_reassignment`** covers all seven `ImportSourceUser*` workflow mutations: they are all state transitions on an existing source-user mapping (reassign, cancel, keep as placeholder, resend, retry, undo).
- **`AwardEmojiToggle`** declares both `create_award_emoji` and `delete_award_emoji` since its effect depends on the current state.
- **`Achievements::UserAchievement`** gains a `delegate :namespace, to: :achievement` so the boundary extractor can reach the group from `user_achievement_id`.
- **Instance boundary for user custom attributes:** `UserCustomAttributeSet`/`DeleteUserCustomAttribute` are admin-only operations on arbitrary users, so they use the `instance` boundary (the existing custom attribute assignable permissions already declare it).
- **Timelogs declare only the `project` boundary.** Time tracking on group-level work items is not an established flow to assert a group success path against, so no group boundary is declared.
- **Achievements/import mutations on personal namespaces:** `Achievements` and `Import::SourceUser` can technically belong to personal (user) namespaces; only the `group` boundary is declared, matching the existing `placeholder_reassignment` assignable permissions and the primary product flows.
